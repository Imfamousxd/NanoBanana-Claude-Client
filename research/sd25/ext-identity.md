# Seedance 2.5 `video_extension` — does identity and voice carry across the seam?

Measured against the live ModelArk API, 2026-08-07/08. 4 generations spent (budget 4).
Every number below came from ffprobe/ffmpeg/Praat/faster-whisper on downloaded files, not from
submit-acceptance and not from the vendor docs.

---

## VERDICT

**YES — and it is the only route past 30s that keeps the person.**

Extension is not "a second generation conditioned on a reference". It **resumes the source clip**:
the extension's first frame is a re-render of the base's last frame at **PSNR 31.26 dB / SSIM 0.907**,
while two frames **one second apart inside a single take** measure only **16.18 dB / 0.762**. The seam
is more continuous than any ordinary cut inside the same take. Face, hair, wardrobe, earring, sun
position, sun flare, background boats and water all carry. Voice carries with no register jump
(median F0 181.0 Hz before the seam, 181.7–197.6 Hz after, inside the base's own 181–206 Hz swing).
The extension speaks **new dialogue you supply, verbatim and lip-synced** — bilabial closure lands on
the exact frame of the /p/ in "pack".

Three things sharpen the verdict:

1. **The output is the extension ONLY** — 10.000s or 30.000s, never base+extension. You concatenate locally.
2. **Cost is charged on input seconds too**: `tokens = 21,600 × (input_video_seconds + output_seconds)`,
   measured three times. Extending the 30s master costs **4×** what extending the last 10s hop costs,
   for the same 10s of new footage.
3. **The voice measurements cannot certify identity on their own** — they prove no *discontinuity*.
   The same F0/centroid/formant/MFCC instruments fail to separate a **known recast** (a second 30s
   generation of the same prompt, visibly a different woman) from the base. The discriminating
   evidence for "same person" is visual. Stated honestly below rather than dressed up.

Practical ceiling as measured: **30s base + 30s extension = a 60s continuous talking head in two calls**,
identity held to t=59.5. A second hop (extend the extension) also held, giving 30+10+10 = 50s.

## 1. THE CALL SHAPE (measured, first generation)

Endpoint and auth are unchanged from the existing law bank. The extension-specific parts:

```json
POST https://ark.ap-southeast.bytepluses.com/api/v3/contents/generations/tasks
{
  "model": "dreamina-seedance-2-5-260628",
  "content": [
    { "type": "text",
      "text": "Extend @Video 1 forward. Continue the same unbroken handheld selfie take — no cut,\nno new shot, no change of person, wardrobe or location. ...\nShe says: \"Oh — and the entries stack. ...\"\nAudio: her own voice only ... No music, no soundtrack." },
    { "type": "video_url",
      "video_url": { "url": "<ORIGINAL TOS url of a prior 2.5 output>" },
      "role": "reference_video" }
  ],
  "generate_audio": true,
  "ratio": "adaptive",
  "duration": 10
}
```

Three corrections to how this repo has been calling 2.5:

- **`ratio` and `duration` ride as TOP-LEVEL fields here, not as trailing `--flags`, and they are
  honoured.** The task echo returned `"duration": 10` and `"duration": 30` exactly as sent. This is
  the shape in ByteDance's own "Extend video" cURL example (docs.byteplus.com/en/docs/ModelArk/1520757).
  Both forms evidently work; the doc form is confirmed measured.
- **`role` must be `reference_video`.** Anything else is a hard 400 at submit. Verbatim:

  ```
  {"error":{"code":"InvalidParameter","message":"The parameter `content` specified in the request is
  not valid: reference media mode requires video role to be reference_video. Request id:
  02178614829212850b1c418616fd9b5f78a16c5c9d34162c4a268","param":"content","type":"BadRequest"}}
  ```

- **`ratio` must be `adaptive`** (documented; the output shape follows the input video). The echo
  resolved it to `9:16` and the file measured 720×1280.

The prompt refers to the video part as **`@Video 1`** — positional, 1-indexed over the media parts.

**Why a photoreal human video is accepted at all**, when a photoreal human `first_frame` is refused
with `InputImageSensitiveContentDetected.PrivacyInformation`: ModelArk has an explicit carve-out —
*"ModelArk trusts face-containing videos generated by these models. You can use the original
face-containing videos generated by these models under your account within the past 30 days as input
assets"* (docs 1520757 / 2608626). Constraints stated there: same account, same platform, **original
model output only** — *"they cannot be used after secondary editing"*, and *"compressing or forwarding
files may invalidate trust verification"*. The generated URL itself is signed for **24 hours**.

## 2. THE SEAM IS MORE CONTINUOUS THAN A CUT INSIDE THE SAME TAKE

Base take: `generations/gh-explainer/explainer-v2-30s.mp4` (task `cgt-20260808080225-vxczg`,
30.041667s, 720×1280, 24fps, AAC 32 kHz stereo).

| Comparison | PSNR (dB) | SSIM |
|---|---|---|
| **SEAM G1** base last frame → extension first frame | **31.26** | **0.907** |
| **SEAM G3** base last frame → 30s-extension first frame | **31.97** | **0.918** |
| **SEAM G2** ext1 last frame → hop-2 first frame | **39.45** | **0.961** |
| SEAM G4 (trigger words removed) ext1 last → G4 first | 35.36 | 0.938 |
| control — base t=29.00 vs base last frame (1.0s apart, one take) | 16.18 | 0.762 |
| control — base t=28.00 vs base last frame (2.0s apart, one take) | 16.86 | 0.749 |
| control — ext t=0 vs ext t=1.0 (1.0s apart, one take) | 12.59 | 0.673 |
| control — base t=15 vs base last frame (15s apart, one take) | 11.10 | 0.549 |
| **ceiling — base t=15 vs v1 t=15 (two separate 30s generations, same prompt)** | **11.11** | **0.418** |

Read it this way: the across-seam distance (31–39 dB) is **an order of magnitude tighter** than the
distance between two frames one second apart inside a single continuous take (12–17 dB). It is not a
byte copy — 31 dB means the moment is *re-rendered*, not pasted — but the pose, expression, hair,
lighting, lens flare and background are reproduced.

The recast ceiling is real and obvious: the two separate 30s generations of the same prompt
(`explainer-30s-base.mp4` v1 vs `explainer-v2-30s.mp4` v2) are **two different women** — v1 has long
loose mid-brown hair, a beige crew-neck top and green eyes; v2 has blonde hair pulled back tight,
bare shoulders, brown eyes and heavier freckling. Frames: `research/sd25/ext/frames/v1_t15.00.png`
vs `base_t15.00.png`.

Identity 59.5 seconds into the assembled piece (`G3-ext30_t29.5.png`) is still v2: same brow shape,
same freckle field, same small gold earring, same pulled-back blonde hair, same marina.

## 3. VOICE — NO REGISTER JUMP, AND AN HONEST NOTE ON THE INSTRUMENT

Praat (parselmouth), voiced frames only, pitch floor 75 Hz / ceiling 500 Hz; formants Burg 5/5500 Hz;
`cent` = spectral centre of gravity (power 2).

| segment | f0_med | f0 p25–p75 | cent | F1 | F2 | F3 | F4 | jitter | shimmer |
|---|---|---|---|---|---|---|---|---|---|
| BASE 0–10 | 205.6 | 174.6–252.8 | 791 | 516 | 1579 | 2932 | 4061 | .0149 | .0844 |
| BASE 10–20 | 185.4 | 169.9–214.3 | 768 | 584 | 1603 | 2907 | 4163 | .0152 | .1053 |
| **BASE 20–30 (before seam)** | **181.0** | 165.8–214.5 | **770** | 486 | 1693 | 2876 | 4001 | .0236 | .1164 |
| **EXT1 0–10 (after seam)** | **209.1** | 184.8–255.1 | 728 | 464 | 1498 | 2934 | 4128 | .0183 | .0868 |
| EXT1 0–5 (continues the base's laugh) | 244.7 | 206.6–293.7 | 772 | 445 | 1408 | 3069 | 4121 | .0174 | .0731 |
| EXT1 5–10 (settled speech) | 189.1 | 179.8–214.7 | 675 | 483 | 1540 | 2870 | 4108 | .0194 | .1081 |
| EXT2 hop-2 0–10 | 213.8 | 187.8–252.3 | 750 | 559 | 1433 | 2977 | 4031 | .0180 | .1113 |
| G3 ext30 0–10 | 197.6 | 171.9–236.0 | 784 | 549 | 1508 | 3000 | 4133 | .0215 | .1106 |
| G3 ext30 10–20 | 181.7 | 165.6–197.5 | 693 | 527 | 1356 | 2964 | 4065 | .0156 | .1066 |
| G3 ext30 20–30 | 183.3 | 159.8–203.3 | 767 | 515 | 1594 | 2905 | 4199 | .0249 | .1327 |
| *ceiling* — v1 0–10 (**known recast**) | 186.7 | 166.8–207.8 | 642 | 518 | 1623 | 3061 | 4089 | .0173 | .0993 |
| *ceiling* — v1 20–30 (**known recast**) | 193.3 | 158.8–235.7 | 720 | 492 | 1651 | 2907 | 4001 | .0197 | .0997 |
| *ceiling* — ugc-01 (diff gen, diff woman) | 186.1 | 168.2–201.5 | 596 | 544 | 1581 | 2858 | 4040 | .0194 | .1019 |
| *ceiling* — edu-01 (diff gen, male-register voice) | 103.1 | 93.4–117.8 | 470 | 414 | 1563 | 2678 | 3739 | .0389 | .1057 |

**What this shows.** The seam delta (181.0 → 189.1 settled, or → 181.7/183.3 across the 30s
extension) is **smaller than the base take's own internal swing** (181.0 → 205.6). Spectral centroid
moves 770 → 675–784, again inside the base's own 768–824 range. Every formant median in every
extension segment sits inside the base's own within-take range (F1 486–584, F2 1579–1693,
F3 2685–2932, F4 3878–4163). Level and room tone match too: base tail speech level −11.7 dBFS /
noise floor −43.3 dBFS, extension −10.9…−11.2 / −43.8…−44.4. **There is no measurable discontinuity
at the seam.**

**What this does NOT show — say it out loud.** These instruments cannot separate a *known recast*
from the base. v1 is provably a different woman, yet its f0 (186.7 / 193.3) and formants land inside
the same band. An MFCC-mean cosine fingerprint is worse still:

```
SEAM      base_20_30 vs ext_0_10                                    cos_d = 0.0206
FLOOR     base_10_20 vs base_20_30 (same take)                      cos_d = 0.0219
FLOOR     base_0_10  vs base_20_30 (same take)                      cos_d = 0.0456
CEILING   base_20_30 vs v1_20_30 (diff generation, same prompt)     cos_d = 0.0086   <-- BELOW the floor
CEILING   base_20_30 vs edu01   (diff generation, diff voice)       cos_d = 0.1579
```

A known recast scores *closer* than two halves of one take, because the metric is dominated by the
shared marina ambience and the model's shared voice character. Only the male-register control
separates. **Conclusion: F0 / centroid / formants / MFCC-mean are usable as discontinuity detectors
and are NOT usable as speaker-identity gates for two same-scene female generations from this model.**
Anyone building a voice-identity gate on these numbers will pass a recast.

The one voice figure that looks like a jump — EXT1 0–5s at f0 244.7 Hz — is not a recast. The base
ends mid-laugh, and the extension resumes mid-laugh; laughter is high-F0. By 5–10s it is 189.1 Hz.

## 4. THE EXTENSION SPEAKS NEW DIALOGUE, VERBATIM AND LIP-SYNCED

faster-whisper `small.en`, on the downloaded files.

**G1 (10s).** Written: `"Oh — and the entries stack. The app counts them for you, so you can see mine
sitting there at forty. Draw closes end of the month. Go check your pack."`
Transcribed:

```
[  0.00-  6.12] Oh, and the entries stack the app counts them for you so you can see mine sitting there at 40
[  6.40-  9.38] Draw closes end of the month. Go check your pack
```

Word-for-word (only "forty"→"40", a whisper normalisation). 31 words over 9.38s = **3.3 words/sec**.

**G3 (30s, four timed beats).** All four beats delivered, in order, near-verbatim, and the beat
boundaries land within 0.9s of the written marks (written 0-8 / 8-16 / 16-24 / 24-30; delivered
beat 2 at 8.84, beat 3 at 16.08, beat 4 at 24.36). 87 written words → 2.97 w/s delivered against
2.90 w/s written. **Timed beats and the words/sec pacing law survive into an extension unchanged.**

**Lip sync is native, and it is measurable rather than a matter of opinion.** A filmstrip of
G1 at 8 fps over 8.5–9.5s (`research/sd25/ext/frames/strip_G1_8.5-9.5.png`) shows the lips **fully
closed at t = 9.000** and **wide open at t = 9.125** — the /p/ closure and release of "pack", the last
word of a segment whisper ends at 9.38, after which the mouth settles into a closed smile.

An audio-envelope × mouth-region-motion cross-correlation was also run, and **it should not be used**:
it scores the operator-approved base take at only r = 0.054, so it fails to validate on a known-good
clip. (For the record it scored the extension highest of the three clips tested, r = 0.365 at −125 ms.)
Reported here so nobody rebuilds it thinking it works.

## 5. WHAT COMES BACK, AND WHAT IT COSTS

**The output is the extension only.** Both 10s extensions measured exactly 10.000s and the 30s
extension exactly 30.000s — never 40s or 60s. Container matches the base exactly (720×1280, 24 fps,
h264, AAC 32 kHz stereo), so `ffmpeg concat` joins them without re-encode.

**Billing follows input + output seconds.** Measured on four tasks:

| task | input video | output | total_tokens | 21,600 × (in+out) |
|---|---|---|---|---|
| `cgt-20260808082152-qcl55` (G1) | 30s | 10s | 864,000 | 21,600 × 40 ✓ |
| `cgt-20260808083339-ntbs8` (G2) | 10s | 10s | 432,000 | 21,600 × 20 ✓ |
| `cgt-20260808083807-xqbnp` (G3) | 30s | 30s | 1,296,000 | 21,600 × 60 ✓ |
| `cgt-20260808084616-m2dcp` (G4) | 10s | 10s | 432,000 | 21,600 × 20 ✓ |

(reference points: a 5s t2v = 108,900 and a 30s t2v = 648,900, i.e. 21,600/s + 900 fixed. The
extension rows carry no +900 and bill the source video as if it were generated footage.)

**So chain from the last hop, not from the master.** Extending the 30s master by 10s costs 864,000
tokens; extending the previous 10s hop by 10s costs 432,000 for the same 10s of new footage. The
identity result was as good or better on the cheap route (hop-2 seam 39.45 dB vs 31.26 dB).

Wall clock: 10s extension of a 30s source = 250s; 10s of a 10s source = 137s and 172s; 30s of a 30s
source = 342s.

## 6. THE TRIGGER PHRASE IS SOFTER THAN THE DOCS IMPLY

Doc 2607688 says 2.5 classifies each request into one of five task types "based on the value of
`content.role` **and the prompt intent**", and that video extension requires *"at least one extension
trigger keyword or phrase, such as extend forward/backward, continue, or continue the story"*.

G4 is G2 with exactly one variable changed: the opening `"Extend @Video 1 forward. Continue the same
unbroken handheld selfie take"` became `"@Video 1. The same unbroken handheld selfie take"`. Same
source video, same dialogue, same duration, same audio direction.

Result: **still a frame-continuous extension** — 35.36 dB / 0.938 against the source's last frame,
same woman, dialogue verbatim. Slightly looser than the 39.45 dB the trigger phrase bought, but
nowhere near a recast.

Caveat, stated precisely: the G4 prompt still carried continuity *intent* ("the same unbroken
handheld selfie take — no cut, no new shot, no change of person, wardrobe or location"). What is
measured is that the literal words "extend"/"continue" are not required. A prompt with **no**
continuity language was not tested.

## 7. HARD LIMITS THAT SHAPE LONG-FORM

- **Reference video: 2–30s each, ≤30s total, ≤10 videos, ≤200 MB, fps 24–60, 300–6000 px per side,
  total pixels 409,600–8,295,044, aspect 0.4–2.5, mp4/mov h264/h265 + AAC/MP3** (docs 1520757).
  Consequence: **a chain can never re-show the model more than 30s of context.** Long-form is a chain
  of ≤30s windows, and hop N only sees hop N−1.
- The 30.041667s base was **accepted** despite the documented 30s ceiling — the cap is not enforced
  at +0.04s. Do not lean on that.
- Trust window: original output URL signed for **24 hours**; trust as an input asset lasts **30 days**
  from generation, same account, **original bytes only**.

## STILL UNKNOWN

- **Hops 3+.** Only two hops were chained (50s assembled). Whether drift compounds over 4-6 hops the
  way 1.5-pro's re-render drift did is untested — and it is the thing to test next, because the cheap
  chain (extend the last hop) is exactly the pattern that would accumulate it.
- **A prompt with no continuity language at all** — does it recast? G4 removed the keywords but kept
  the intent.
- **Re-hosted / re-encoded source.** Whether the trust carve-out survives copying the ORIGINAL bytes to
  our own public URL (docs say mirroring to TOS is the recommended route, but "compressing or
  forwarding may invalidate"), and what the refusal looks like for a locally re-encoded copy. This
  decides whether the 24-hour URL is a hard production deadline.
- **Extending backward** ("continue the 5 seconds before @Video 1") — documented, untested.
- **`duration: -1`** (model chooses) on an extension — documented, untested.
- **`output_format: "mov"`**, which the docs recommend specifically for extension — untested; may
  change seam colour/brightness continuity.
- **reference_image alongside reference_video in an extension** (e.g. holding up the real card during
  the extended half) — untested.
- **Whether a policy-refused or async-failed extension is billed.** No failure occurred in this pass.
- **The true input duration ceiling.** 30.041667s was accepted; nothing longer was tried.
- **A real speaker-identity instrument.** Nothing available offline discriminated. If voice identity
  ever needs gating, it needs a speaker-embedding model, not the measures used here.
